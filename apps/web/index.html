Why it slips through

A leak doesn’t throw an error.

When a policy or a route is too generous, Supabase still answers with a 200. The only difference is whose rows come back, and nothing in your logs will point it out.

In 2025, 170 of 1,645 apps from one AI app builder’s showcase let anyone read their tables with the public key (CVE-2025-48757).

How it checks

Row rules guard one door. Pyx tries all three.

Same test users, same records, every way your app can hand them out.

GET /rest/v1/invoices

Database API

The table as your frontend reads it, with each user’s real sign-in. This is where row-level security applies.

GET /rest/v1/rpc/get_invoice

RPC functions

Functions marked security definer skip row rules unless they check the caller themselves. Pyx calls them as each user.

GET /api/invoices/:id

Your API routes

Server code that uses the service key skips row rules completely. Pyx sends each user’s token to your route and reads what comes back.

Setup

Three steps, then it runs on every pull request.

1

Write down who sees what

Point Pyx at a table and it drafts the rule: owners read their own rows, nobody else does.

pyx init --table invoices --owner-column owner_id
2

Have the owner sign off

The person responsible approves that exact rule. A later pull request can’t quietly change it.

pyx approve --acknowledge sha256:d46d…
3

Check every release

CI starts a throwaway copy of your database, signs in as the test users and tries every path.

pyx run --html report.html
Reports

Something you can hand a client.

Each run can write a one-page report: the result, who could see which record, and what to do about anything that failed.

  • Readable by non-engineers. “Alice could open Bob’s invoice through /api/invoices” instead of a stack trace.
  • Traceable. The approved rule, the commit, and whether there were uncommitted changes.
  • Safe to forward. No tokens, keys or real rows are ever written into it.

Quick start

Or run it yourself.

In your Supabase project
$ npm install -g pyx-cli
$ supabase start
$ pyx init --table invoices --owner-column owner_id --marker-column title
$ pyx fixture provision --rule invoices-owner-read.rule.json
$ pyx doctor --rule invoices-owner-read.rule.json --credentials .pyx/local.env
$ pyx run --store .pyx/approvals --rule invoices-owner-read --credentials .pyx/local.env --html report.html
FAQ

Questions people ask first.

Do you need our production database or keys?

No. Pyx runs against a throwaway local copy built from your migrations, with made-up users and records. A setup works from your repository and arrives as a pull request.

We already have Supabase’s advisor and some pgTAP tests.

Keep them. The advisor flags tables with no rules, and pgTAP checks SQL directly. Pyx goes through the same doors your app uses, with real sign-ins, including RPC functions and your own API routes, where row rules don’t apply.

Is this a penetration test?

No. It checks one thing very carefully, on every release: whether one customer can see another customer’s data. Get a security review for everything else.

What if we use teams or workspaces?

Automatic checks cover tables where each row has one owner. Team membership is next on the roadmap; until then we set those rules up by hand as part of release review.

Does Pyx change our code or use AI?

No. Runs are read-only and give the same answer every time. Someone on your team approves every rule.
