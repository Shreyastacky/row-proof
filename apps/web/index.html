How it works

Agree the rule once. Prove it every release.

The person responsible for the data approves the expectation. Code changes, including AI edits, can’t quietly change it.

01 · Approve

A readable permission matrix

Who may read which record, as a short JSON rule. The owner reviews a plain diff and approves one exact content hash. Any later change to intent needs a new approval.

02 · Prove

Real requests, real identities

Synthetic users sign in for real. Each read goes through the Supabase Data API with a verified token. Owner reads are positive controls; timeouts, 404s and errors never count as a pass.

03 · Keep

In CI, on every pull request

The approved baseline is read from your protected branch, never from the PR. A leak fails the build (exit 1), with JUnit output, a PR summary and a client-ready HTML report.

Evidence

What a pass means

Precise claims, on purpose

  • The listed assertions held, on the named target, at that time.
  • Identities were verified by your Auth service; records were verified through a separate channel.
  • Every control was established. Anything less is blocked, never green.
What it doesn’t claim

No security theatre

  • Not a pentest, certification, or proof your whole app is secure.
  • Today: SELECT on user-owned tables via the Data API. Writes, tenants and shared records are scoped manually for now.
  • Not production evidence. Checks run on a disposable copy built from your migrations.

FAQ

Straight answers

Do you need access to our production database or keys?

No. RowProof runs against a disposable local Supabase stack built from your migrations, with synthetic users and records. For a Boundary Check we work from your repository (or a copy of your migrations) and deliver a pull request.

How is this different from pgTAP tests?

pgTAP is great, and you can keep it. RowProof tests through the same Data API and Auth path your app uses, with real tokens. It treats errors and timeouts as “blocked” instead of “denied”, and keeps the expected access approved separately from code, so a pull request can’t quietly redefine “correct”. It also produces evidence a non-engineer can read.

Does it replace a penetration test or security review?

No. It continuously checks one important class of bug, cross-user data exposure, against an agreed rule. Pair it with a security review for everything else.

We use multi-tenant organizations, not per-user rows.

Automated support today is single-owner tables. Tenant membership rules are on the roadmap. Until then we scope them by hand as part of Release Assurance. Ask us with a short description of your model.

Is it AI? Will it change our code?

No. RowProof is deterministic and read-only during a run. It never edits policies, approvals or your application. AI may help draft a rule; only a human approves it.

What does the license allow?

FSL-1.1 lets you use, modify and run RowProof for free for any purpose except offering a competing product or service. Each release converts to Apache-2.0 after two years.
