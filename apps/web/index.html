01  Why it slips through

A leak and a denial look the same from the outside.

GET /api/invoices/inv_b as Alice
200 OK { "invoice": null }
Denied. As intended.
GET /api/invoices/inv_b as Alice
200 OK { "invoice": { "owner": "bob", "total": 3400 } }
Bob’s invoice. A leak.

No error, no alert, nothing in the logs. Uptime checks pass. Scanners that try your public key see a stranger getting nothing. Only a check that signs in as Alice and knows she must not see Bob’s invoice can tell these apart.

08  Questions

We already have Supabase’s Security Advisor and some pgTAP tests.

Keep them. The advisor flags tables without rules, and pgTAP tests SQL directly. Pyx goes through the doors your app actually uses, as real signed-in users, including RPC functions and your own routes where row rules don’t apply.

Do you need access to our production project?

No. Pyx starts a disposable copy from your migrations, creates synthetic users and records, and tests that. It refuses to touch any existing user or row that isn’t one of its own.

What happens when a check fails?

The run exits 1 and the pull request shows who gained access, to which record, through which route. pyx repro writes a short README and a curl script that replays the failing request against your local copy.

What if the test setup itself is broken?

Then nothing passes. Expired tokens, two users who are secretly the same account, a test record that changed mid-run or a stack that isn’t reachable all end as “blocked”, never as a green check.

Who approves the rules?

The person responsible for the data. They approve an exact version of the rule, and CI reads it from your protected branch, so a pull request can’t quietly redefine what “correct” means.

What doesn’t it cover?

Writes, list queries, team and workspace membership, storage and edge functions are not checked automatically yet. We publish what Pyx misses in the benchmark.
