The problem

Row Level Security doesn’t fail loudly. It fails politely.

On Supabase, RLS is often the only thing standing between one customer and the next. A policy that is a little too generous raises no error. It quietly returns someone else’s rows, and policies are now rewritten by AI tools between releases.

Method

Agree the rule once. Prove it every release.

The person accountable for the data approves the expectation. Code changes, including the ones an AI assistant writes, cannot quietly redefine what correct means.

01 — Approve

A matrix the owner can read

Who may read which record, written as a short rule. The owner reviews a plain diff and approves one exact content hash. Any change of intent needs a new approval.

02 — Prove

Real requests, real identities

Synthetic users sign in for real and read through the Supabase Data API with verified tokens. Owner reads are positive controls, so a broken route can never pass as “protected”.

03 — Keep

On every pull request

The approved baseline is read from your protected branch, never from the change under review. A leak stops the build and leaves a report a client can read.

The difference

Scanners ask what strangers can see. RowProof asks what each user should.

Public-key scanners catch tables left open, and you should run one. They cannot know that a signed-in customer must never read another customer’s invoice. That knowledge is your intent, and RowProof keeps it.

What a pass means

Precise, on purpose.

  • The listed expectations held, on the named target, at that moment.
  • Identities were verified by your Auth service; records through a separate channel.
  • Every precondition was established. Anything less is reported as blocked, never as a pass.
What it does not claim

No security theatre.

  • It is not a penetration test, a certification, or proof that an entire application is secure.
  • Today it covers reads of user-owned tables through the Data API. Tenant and shared-record rules are scoped by hand.
  • It is not production evidence. Checks run on a disposable copy built from your migrations.
Run it yourself

The CLI is free. It always will be.

Source-available under FSL-1.1, with each release becoming Apache-2.0 after two years. Use it on your own applications, and in work for your own clients, at no cost.

Inside your Supabase project
$ npm install -g rowproof
$ supabase start
$ rowproof init --table invoices --owner-column owner_id --marker-column title
$ rowproof fixture provision --rule invoices-owner-read.rule.json
$ rowproof propose --rule invoices-owner-read.rule.json --store .rowproof/approvals --proposed-by me --out p.json
$ rowproof approve --proposal p.json --store .rowproof/approvals --approver owner --acknowledge <hash> --promote
$ rowproof run --store .rowproof/approvals --rule invoices-owner-read --credentials .rowproof/local.env --html report.html

Questions

Straight answers.

Do you need access to our production database or keys?

No. RowProof runs against a disposable local Supabase stack built from your migrations, with synthetic users and records. A Boundary Check works from your repository, or a copy of your migrations, and arrives as a pull request.

How is this different from writing pgTAP tests?

Keep your pgTAP tests. RowProof checks through the same API and sign-in path your application uses, treats errors and timeouts as blocked rather than denied, and keeps the expected access approved apart from code, so a pull request cannot quietly change what correct means. It also produces evidence a non-engineer can read.

Does it replace a penetration test?

No. It continuously checks one class of failure that matters a great deal, cross-customer data exposure, against a rule your team agreed. Pair it with a security review for everything else.

We use organisations and teams, not per-user rows.

Automated support today covers single-owner tables. Tenant membership is on the roadmap; until then we scope those rules by hand within Release Assurance.

Is it AI? Will it change our code?

No. RowProof is deterministic and read-only while it runs. It never edits policies, approvals or your application. An assistant may help draft a rule; only a person approves it.

What does the licence allow?

FSL-1.1 lets you use, modify and run RowProof for any purpose except offering a competing product or service, including in professional work for your own clients. Each release becomes Apache-2.0 two years after it ships.
